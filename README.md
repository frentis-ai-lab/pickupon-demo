# 픽업온 Sprint 1 데모 앱

하루빈 커피 역삼점의 모바일 픽업 주문 서비스 '픽업온'의 Sprint 1 결과물입니다. 셀타스퀘어 사내교육 2일차의 스프린트 리뷰 시연에 씁니다.

- 교육용 가상 사례입니다. 회사, 브랜드, 인물, 수치는 모두 가상입니다.
- 기능, 정책, 인수조건, 결함은 `../BIBLE.md`를 따릅니다.
- 인수조건 4번(21:00 정각 주문 거절)을 어기는 결함을 일부러 넣어 두었습니다. 아래 '결함' 절을 보십시오.

## 실행

Node.js 22 이상(LTS 24 권장)과 pnpm이 필요합니다. 빌드 단계는 없습니다.

```bash
pnpm install
pnpm start             # 기본 포트 4300, 0.0.0.0에 바인딩
PORT=5000 pnpm start   # 포트 바꾸기
pnpm dev               # 파일을 고치면 서버가 저절로 다시 켜집니다(결함 수정 시연용)
pnpm test              # 인수조건 시험. 지금은 조건 4만 실패하고 종료 코드 1로 끝납니다
```

DB 없이 메모리에 저장합니다. 서버를 다시 켜면 주문이 비워지고 메뉴 8개만 남습니다.

## 화면 주소

| 주소 | 화면 |
|---|---|
| `/demo` | 시연 화면. 왼쪽은 휴대폰 틀 안의 고객 화면, 오른쪽은 태블릿 틀 안의 매장 화면입니다. 1790×928 창에 맞췄습니다. |
| `/demo?view=zoom` | 고객 화면을 1.35배로 키우고, 옆에 '메뉴 옵션 고르기' 인수조건과 지금 고른 옵션을 보여 줍니다. 상단 [고객 화면 크게] 버튼과 같습니다. |
| `/` | 고객 화면(폭 390px 기준). 메뉴 목록 → 옵션 → 장바구니 → 주문하기(테스트 결제) → 주문 완료(주문번호, 주문 내용, 픽업 안내) |
| `/store` | 매장 화면(태블릿 가로). 새 주문 목록과 [제조 시작] [픽업 대기] [전달 완료] |
| `/acceptance` | 인수조건 점검표. '장바구니에 담아 주문하기' 조건 1~5를 실제 API로 실행합니다. |

다른 기기에서 열 때는 `http://<이 장비의 이름이나 IP>:4300/demo`로 접속합니다.

시연 화면 상단 막대에서 할 수 있는 일은 다음과 같습니다.

- 시연 시각: [실제 시각] [06:59] [07:00] [20:59] [21:00] [21:01] 또는 직접 지정. 서버가 이 시각으로 영업시간을 판단합니다. 시각을 고정하면 초가 흐르지 않습니다.
- 데이터 초기화: 두 번 눌러야 실행됩니다. 주문을 모두 지우고, 주문번호를 101부터 다시 매기고, 시연 시각을 실제 시각으로 돌립니다. 고객 화면의 장바구니도 비웁니다.
- 인수조건 점검표: 새 탭으로 `/acceptance`를 엽니다.

### API

| 요청 | 하는 일 |
|---|---|
| `GET /api/menu` | 메뉴 8개와 옵션 가격 |
| `GET /api/clock`, `PUT /api/clock` | 시연 시각 읽기와 바꾸기. `{"time":"21:00"}` 또는 `{"mode":"real"}` |
| `POST /api/orders` | 주문하기(테스트 결제). 빈 장바구니는 400, 영업시간 밖은 409와 안내 문구 |
| `GET /api/orders/:no` | 주문 한 건(주문 완료 화면이 주문번호와 주문 내용을 읽음) |
| `GET /api/store/orders` | 매장 주문 목록. 오래된 주문이 위, 새 주문이 맨 아래 |
| `POST /api/store/orders/:no/status` | 상태를 다음 단계로 바꾸기. `{"status":"making" \| "ready" \| "done"}` |
| `POST /api/demo/reset` | 시연 데이터 초기화 |
| `POST /api/acceptance/run` | 인수조건 1~5 실행 결과 |

## 시연 순서(강사용)

준비: 브라우저 창을 1790×928로 두고 `/demo`를 엽니다. [데이터 초기화]를 두 번 누릅니다. 수업 시간대라면 시연 시각은 [실제 시각]으로 둡니다. 출근 시간 느낌을 내려면 직접 지정 칸에 08:20을 넣고 [지정]을 누릅니다.

1. 정상 주문(조건 1). 고객 화면에서 아메리카노를 눌러 ICE, Large, 샷 추가 1을 고르고 담습니다. 가격이 4,000원에서 5,000원으로 바로 바뀌는 것을 보여 줍니다. 크루아상도 담고 [장바구니 보기] → [주문하기] → 이름과 끝 4자리 → [테스트 결제]를 누릅니다. 주문번호가 나오고, 오른쪽 매장 목록 맨 아래에 같은 주문이 '새 주문'으로 강조되어 3초 안에 나타납니다.
2. 매장에서 상태 바꾸기. 매장에서 [제조 시작] → [픽업 대기] → [전달 완료]를 차례로 누릅니다. 고객 화면은 주문번호, 주문 내용, "매장에서 이름(끝 4자리)을 부르면 받아 가세요" 안내만 보여 주고 진행 상태는 보여 주지 않습니다. '내 주문 상태 확인' 스토리는 Sprint 1에서 시작하지 못했기 때문입니다.
3. 영업시간 밖(조건 3, 5). 시연 시각을 [21:01]로 두고 주문하면 "지금은 주문할 수 없습니다(영업시간 07:00~21:00)"가 나오고 매장 목록에는 아무것도 생기지 않습니다. [06:59]도 같습니다. [07:00]은 접수됩니다.
4. 결함 발견(조건 4). [20:59]에 주문하면 접수됩니다. [21:00]에 주문해도 접수됩니다. "21:00 정각부터 받지 않기로 합의했는데, 이 스토리를 완료로 셀 수 있을까요?"라고 묻습니다.
5. 인수조건 점검표. [인수조건 점검표]를 열면 조건 4만 실패합니다. 스토리는 완료로 세지 않고 결함으로 기록해 Sprint 2로 넘깁니다(BIBLE 7장).
6. 리뷰 의견 재료. 화면에서 다음을 짚습니다.
   - 오미경 점장: 새 주문이 와도 소리가 나지 않습니다. 매장 화면에는 알림음이 없습니다. 인수조건에 없던 새 요구입니다.
   - 정승호 대표: 샷 추가 버튼(+, −)은 28px로, 옵션 버튼(48px)이나 수량 버튼(44px)보다 작습니다. [고객 화면 크게]로 보여 주면 잘 보입니다. 인수조건과 DoD에 크기 기준이 없었으므로 토론 거리입니다.
   - 직원 테스트: 주문이 끝나면 카톡으로 받고 싶다는 의견입니다. 앱에는 알림이 없고, 백로그의 '제조 완료 알림 받기'에 의견을 붙입니다.
7. (선택) 결함 고치기. `pnpm dev`로 켠 상태에서 아래 '결함' 절의 한 줄을 고칩니다. 서버가 다시 켜지면 점검표에서 [다시 실행]을 눌러 5개 모두 통과하는 것을 보여 줍니다. 끝나면 `git checkout src/hours.js`로 결함을 되돌려 둡니다.

## 결함: 21:00 정각 주문이 접수됨

- 위치: `src/hours.js` 10행, `isWithinBusinessHours`
- 지금 코드: `return time >= OPEN_AT && time <= CLOSE_AT;`
- 원인: 종료 시각을 '포함'(`<=`)으로 비교해 21:00:00을 영업시간 안으로 판단합니다. 정책은 "21:00 정각부터 주문을 받지 않는다"입니다. "07:00~21:00" 표기만 보고 양 끝을 모두 포함한다고 읽은 경우입니다.
- 고치는 법(한 줄): `return time >= OPEN_AT && time < CLOSE_AT;`
- 확인: `pnpm test`가 5개 모두 통과하고, `/acceptance`에서 [다시 실행]을 누르면 5/5가 나옵니다.
- 참고: 시연 시각을 [21:00]으로 고정하면 시각이 멈춰 있으므로 언제 주문해도 21:00:00으로 판단합니다. 실제 시각 모드에서는 21:00:00부터 1초 동안만 결함이 드러납니다.

## 인수조건 점검 방식

- 조건 1~5는 `src/acceptance.js`에 있습니다. 점검표 화면과 `pnpm test`가 같은 코드를 씁니다.
- 시연 데이터와 섞이지 않도록 같은 코드로 서버를 하나 더 띄웁니다(127.0.0.1, 빈 포트). 그 서버에 실제 HTTP로 `PUT /api/clock` → `POST /api/orders` → `GET /api/store/orders`를 호출합니다.
- 기대 문구는 BIBLE에서 그대로 옮겼습니다. 앱 코드의 상수를 가져다 쓰지 않으므로 코드가 틀려도 시험은 기준을 지킵니다.
- 조건 2의 "[주문하기]를 누를 수 없다"는 API에서 빈 주문이 거절되는지 확인합니다. 버튼 비활성은 고객 화면의 장바구니에서 눈으로 확인합니다.

`pnpm test` 결과(지금 상태):

```
✔ 조건 1 (정상) 메뉴 2개를 주문하면 주문번호가 나오고 30초 안에 매장 목록에 나타난다
✔ 조건 2 (예외) 장바구니가 비어 있으면 주문할 수 없다
✔ 조건 3 (예외) 영업시간이 아니면 안내 문구를 보여 주고 주문을 저장하지 않는다
✖ 조건 4 (경계) 21:00 정각부터는 접수되지 않는다
✔ 조건 5 (경계) 07:00 정각에 한 주문은 접수된다
```

## Sprint 1 범위에 맞춘 점

- 품절 기능은 없습니다. 품절 기준이 11/25에야 정해지므로 Sprint 1 결과물에는 넣지 않았습니다.
- 매장 화면에 새 주문 알림음이 없습니다. 리뷰에서 나오는 새 요구입니다.
- 결제는 테스트 결제뿐입니다. 결제대행사 가맹 심사를 기다리는 중입니다.
- 고객이 주문을 취소하는 기능은 없습니다. 백로그의 '제조 전 주문 취소하기'입니다.
- 고객 화면에는 진행 상태(접수 → 제조 중 → 픽업 대기 → 전달 완료) 표시와 자동 갱신이 없습니다. '내 주문 상태 확인' 스토리는 Sprint 1에서 시작하지 못했습니다(BIBLE 7장). 주문 뒤에는 주문번호, 주문 내용, 픽업 안내만 보입니다.
- 매장 화면의 [제조 시작] [픽업 대기] [전달 완료]는 그대로 있습니다. '매장에서 새 주문 확인' 스토리는 Sprint 1에서 완료했습니다.
